1项目概述

本项目把飞书消息桥接到本机运行的 coding agent CLI（claude / codex / pi / opencode），并以流式卡片的形式把 agent 的思考、文本输出、工具调用过程实时回投到飞书会话中。它是 TS 项目 lark-channel-bridge 的 Go 复刻。

核心能力：

  • 扫码注册向导：复刻 registerApp 协议（POST accounts.feishu.cn/oauth/v1/app/registration，begin → 二维码 → poll），零手工配置创建飞书应用。
  • 多 profile：配置与会话/工作区隔离存储在 ~/.lark-coding-agent-bridge/ 下。
  • 四种 agent 适配器：spawn-per-message（claude、codex）与常驻进程（pi RPC、opencode HTTP+SSE）两类形态，统一为同一事件流抽象。
  • 流式卡片：CardKit 2.0，400ms 节流全卡更新，飞书客户端呈现打字机效果。
  • 模型反问卡片（ADR-0008 / ADR-0014）：Claude AskUserQuestion / Codex requestUserInput / OpenCode question / Pi extension_ui_request 在飞书弹出交互卡片，用户点选（单题也可直接输入：freeform 卡片带输入框与提交图标，同时支持聊天文字回复）后回填 agent；pending ask 期间暂停 idle 看门狗。交互结束后旧运行卡定格为“已在下方新卡片继续”，后续输出切换到 ask 卡下方新建的流式卡，保证正在更新的消息始终是会话最新一条。Pi 无内置提问工具，反问由社区扩展 npm:pi-ask-user 提供（全局 packages 自动加载，见 implementation.html 3.3）。
  • Codex 工具权限（ADR-0014）：workspace/read-only 时 app-server 的命令执行、文件修改与额外权限请求 → 飞书卡 → 原 JSON-RPC request id 回填；full 保持无审批。
  • OpenCode 工具权限（ADR-0011 / ADR-0018）：server 启动时注入 profile 权限规则；full 全允许，workspace 允许工作区编辑且 shell/网络询问，read-only 拒绝 edit/bash，产生的 ask 事件经飞书卡回填 POST /permission/{id}/reply。这是工具权限约束，不宣称等同于 Codex OS sandbox。
  • Pi 能力对齐（ADR-0019）：原生 RPC 提供模型目录与常驻进程热切换，本地 session JSONL 提供 token/cache/cost 汇总；read-only 只启用内置只读工具，但不宣称等同于 Codex OS sandbox。
  • 聊天访问白名单（ADR-0013）：默认仅应用 owner；/invite user|admin|group 管理名单；陌生人静默丢弃。
  • 三层健壮性：SDK 重连 + supervisor 半死连接检测 + run 级 idle 看门狗；opencode 另加 SSE 帧看门狗（75s 无帧强制重连）与 3s 轮询回补（以服务端消息列表对账，丢帧文本自动补回）。
  • 运维闭环：进程注册表 + dashboard + 自升级。

重点学习参考：deepcoldy/botmux（ask-broker / ask-card / hook 链路）；原版起点 lark-channel-bridge。

2总体架构

单一二进制 cmd/lark-coding-agent-bridge-go 提供 run / dashboard / upgrade / version 四个子命令。run 启动桥接主循环：通过 WS 长连接接收飞书事件，消息经归一化、防抖合并后驱动 agent 运行，运行事件流经状态机归约渲染为卡片，再经节流后通过 CardKit API 推回飞书。

图 1 · 总体架构：单进程内部分层 + 本机 agent 进程 + 注册表/dashboard 侧链
  • 事件入口：internal/lark 基于官方 oapi-sdk-go v3 的 WS 长连接接收消息事件；REST 用于发消息、下载附件；cardkit 用于流式卡片。
  • 消息中枢：internal/bridge 负责消息归一化、600ms 防抖合并（连续多条消息合并为一次运行）、斜杠命令分流；/model 通过可选的 ModelProvider 按当前工作目录读取模型并用一次性 CardKit 卡片切换当前 scope，/usage 通过 UsageProvider 读取 Codex 账户额度或 OpenCode / Pi 本地活动统计。会话按 scope（chat 或 chat:thread）隔离。
  • 运行编排：一次运行 = 下载附件 → 构造 prompt → 调 agent 适配器 → 事件流经 card.Reduce 状态机 → 渲染 → 节流推卡 → 会话持久化。
  • 监督：internal/supervisor 独立于 SDK 重连，做 REST 存活探测并强制重建半死连接。

3Agent 适配层：四种适配器与协议时序

适配层是本项目的设计核心。四种 agent CLI 形态差异极大：两条是「每条消息起一个进程」的 spawn-per-message 模式，两条是「常驻服务」模式。适配层把它们统一收敛为同一抽象：

  • Adapter 接口：Run / Stop / WaitExit。
  • 统一事件流 Event{Type: system | text | thinking | tool_use | tool_result | usage | done | error} —— 上层（卡片状态机、bridge）只消费这一种事件，不感知 agent 差异。
  • SessionResetter 接口：常驻型适配器实现它，用于 /new 重置会话。

各 profile 可配置本机专用的 agent.commandPrefix、shell 与 shellArgs（ADR-0015）。未配置时直接启动 CLI；配置后由短生命周期 shell 先执行前置命令，成功后以 exec "$@" 替换为原 agent 进程。binary 与 argv 通过位置参数传入，不经过 shell 拼接；因此代理环境只影响 agent 子进程及其后代。

启动层先按进程 PATH 解析 CLI；若服务管理器提供的是精简环境（例如 macOS launchd），则继续检查 ~/.volta/bin、~/.local/bin、 ~/.bun/bin、~/.npm-global/bin、~/Library/pnpm、 /opt/homebrew/bin 与 /usr/local/bin 中的可执行文件。显式路径不改写。

Codex、OpenCode 与 Pi adapter 都实现 ModelProvider：Codex 通过 app-server model/list 获取当前账号可见模型，OpenCode 通过目录级 /config/providers 获取当前项目可用模型，Pi 通过临时 sessionless RPC 的 get_available_models 获取目录配置下的模型。Bridge 的 /model 卡片以 15 分钟一次性 nonce 约束回调选项，选择结果写入当前 scope 的 Session.Model（ADR-0016/0018/0019）。三者也实现 UsageProvider： Codex 返回额度窗口，OpenCode 与 Pi 返回本地 session/token/cache/cost 聚合。

4设计决策：为什么不用 ACP

ACP（Agent Client Protocol）是 JSON-RPC over stdio 的 agent 客户端协议。项目初期评估过统一走 ACP 的方案，结论是不采用，各 agent 用其原生机-machine 接口：

图 7 · ACP 决策对比：统一协议 vs 原生协议

保留的 internal/agent/acp.go 最小 ACP client 覆盖：initialize / session/new / session/prompt / session/cancel + session/update 事件翻译 + request_permission 自动放行。由于适配器内部抽象本身与 ACP 语义对齐（且为其超集），未来若要迁移 claude / codex 到 ACP，只需替换适配器实现，上层不动。

5流式卡片机制

agent 事件到飞书客户端「打字机效果」的完整链路：事件 → Reduce（不可变状态机）→ Render（CardKit 2.0 JSON）→ 400ms 节流 + 串行更新队列 → cardkit API → 客户端渲染。

私聊话题回复：chat_type=p2p 时，流式卡片与文本回复走 message.reply 并设 reply_in_thread=true，以用户原消息为根创建/进入话题，主会话时间线不再被长回复刷屏。群聊仍为普通引用回复（不强制开话题）。

ask 后卡片分段：ask 交互卡 settle 后，bridge 先在同一会话/话题中新建 continuation 流式卡，再把 active run、停止/刷新按钮路由和 active-cards.json 指针切到新卡；旧运行卡退出 streaming 并显示“已在下方新卡片继续”。因此连续多轮 ask 时，只有时间线最底部的运行卡继续变化。若新卡创建失败则保留旧 stream，agent 仍可继续，不因展示迁移失败而中断。

私聊会话隔离（ADR-0010）：scope = chatId:topicRoot。主时间线每条用户消息是新话题根 → 新 agent 会话（不把上一条私聊当上下文）；用户在同一飞书话题内续聊时 root_id 相同 → 续同一 session。卡片结束行展示短 session/thread id（🆔）便于核对。群聊 scope 与 bindings 行为不变。

图 8 · 流式卡片链路时序：事件 → 状态机 → 渲染 → 节流 → CardKit → 打字机

5.1 关键设计点

  • 节流与串行：400ms 节流 + 串行更新队列，高频事件合并成帧，只推最新一帧，避免打爆 CardKit 限流。
  • 顺序与幂等：sequence 严格递增；每次更新的 uuid = u_<cardId>_<seq>，网络重试不产生重复更新。
  • 卡片元素：
    • 思考内容 → 折叠面板（thinking）；
    • 正文 → markdown 文本块；
    • 工具调用 → detail 默认折叠（含最新工具与子 agent）；≥3 个时另外合并折叠历史调用，避免 bash 输出随每秒整卡刷新反复改变页面高度；
    • 运行中 footer 以稳定单行显示“当前动作 + 已运行时间”，耗时仍每秒 tick；同时保留 ⏹ 终止按钮（callback cmd=stop）；
    • 终态标注：中断 / 超时 / 错误。
  • 邮箱脱敏：渲染时对文本做邮箱脱敏（MaskEmails）——飞书租户审计会拒绝含原始邮箱地址的卡片。
  • 收尾：card.settings 关闭流式模式，卡片定格为终态。

10私聊建群策略（ADR-0012）

私聊统一话题回复：任意非命令消息进入 p2p scope，流式卡片以用户原消息为根 reply_in_thread，主时间线不被刷屏；会话按话题隔离（ADR-0010）。

不再自动建群：历史 ADR-0006 / ADR-0009 的 LooksLikeTask → escalateP2P 路径已取消（ADR-0012）。话题回复已覆盖「组织任务进度」需求，再启发式建群会造成跳转卡 + 群里双份组织、体验重复。

需要群聊时走显式命令：

  • /new chat [名称] — 立刻建群并拉用户，私聊话题下发跳转卡；
  • /open <序号或 id> — 为 CLI 会话复用已绑定群或新建群（ADR-0007）。

相关实现：internal/bridge/group.go（跳转卡、群名、handleNewChat），intake 不再调用升级逻辑。

设计要点：升级发生在去抖队列之前——把消息 ChatID 改写为新群后再入队，连发消息经 600ms 去抖自然合并成同一批 run；跳转卡片用 https://applink.feishu.cn/client/chat/open?openChatId=<id>，无需分享群链接、一键直达；快捷回复（quick_reply）的私聊提示改用 receive_id_type=open_id 发送，修复了把 open_id 当 chat_id 导致的 230001 invalid receive_id。

11群↔会话关联与 /open 复用（ADR-0007）

群里跑出的 agent 会话需要可被私聊找回：用户私聊 bot → /sessions 看最近会话 → /open <序号> 进入该会话对应的群。若 session 已绑定过群，则复用并下发跳转按钮，绝不重复建群。

11.1 双向存储

  • sessions.json：scope → {sessionId|threadId, cwd}（跑完写入；OpenCode 适配器在 prompt_async 成功后补发 EventSystem{SessionID}）。
  • bindings.json：sessionKey=agent:id → {scope, chatId, chatType}。来源：
    1. 显式 /bind（任意聊天，含 p2p）；
    2. 群 scope runBatch / forwardToGroup 结束后 SetIfAbsent 自动写入（不抢已有绑定）；
    3. /open 新建或复用时写入/刷新。

11.2 /open 流程

  1. 解析序号或 id 前缀（与 /bind 相同的 MatchSession）。
  2. 查 bindings；缺失则用 sessions 反查群 scope 并回填（兼容旧数据）。
  3. 绑定指向的群仍存在且 chat_mode ≠ p2p → 私聊发「群已存在」跳转卡片，结束。
  4. 否则 CreateChat → 写 sessions + bindings → 群欢迎 → 「已创建群」跳转卡片。

与 /bind 的分工：/bind 把会话挂到当前聊天；/open 保证会话有一个群并给一键入口（私聊主场景）。
